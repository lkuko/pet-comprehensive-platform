## 0. 给 AI 开发工具的执行说明（必须先读）

本文件是当前项目的唯一开发基线。开发时必须遵守以下规则：

1. **以本文件为准。** 不得将项目改回 Java / Spring Boot，不得自行更换 FastAPI、Vue、MySQL、Redis 等已确定技术。
2. **按模块化单体实现。** 一个 FastAPI 后端应用，按业务模块和用户端/管理端分包；不拆微服务，不引入服务注册中心、消息队列集群或复杂分布式架构。
3. **必须有两个前端应用。** `admin-web` 是管理端，`user-web` 是用户端。两个前端独立路由、独立布局，但共用同一个后端 API。
4. **必须实现四条核心业务线：** 宠物领养、宠物医疗预约、洗护/寄养服务预约、宠物用品商城。不能只做静态页面或 CRUD 演示。
5. **必须使用 MySQL 持久化业务数据。** 用户、宠物、领养申请、预约、商品、订单等数据不得只放在 Redis。
6. **Redis 的核心用途：** 用户购物车、热点数据缓存、必要的临时状态 / WebSocket 辅助能力。不得把 Redis 当作主数据库。
7. **必须有 JWT 登录认证及角色校验。** V1 角色只实现 `USER`（普通用户）和 `ADMIN`（管理员）；不要擅自扩展成复杂组织、门店、医生多租户权限。
8. **必须实现 WebSocket 管理端业务提醒。** 至少覆盖新领养申请、医疗预约、洗护/寄养预约和商品订单。提醒不能代替数据库记录；消息应在业务数据成功提交后发送。
9. **必须实现未支付商品订单自动关单。** 默认下单 30 分钟未完成模拟支付则关闭订单并释放库存。任务必须可重复执行且不能重复扣减/释放库存。
10. **不接真实微信支付。** V1 仅提供开发演示用的模拟支付流程；不得接入微信支付、支付宝或真实支付 SDK，不得保存银行卡或支付密码。
11. **不做微服务。** 不得在简历、代码注释或项目说明中声称本项目采用微服务架构。
12. **先保证核心闭环，再做美化。** 先完成数据库、登录、管理端数据维护、用户端业务流程、订单状态流转和测试，再补充动画、图表等非核心展示。
13. **不允许只生成代码而不验证。** 每个模块至少完成启动验证、核心接口验证和前端流程验证；修复报错后再进入下一模块。
14. 不得自行检索、克隆、浏览或引用其他项目的代码仓库、开发文档或示例工程；不得要求用户额外提供外部项目作为开发依据。实现仅以当前项目仓库、本文件及用户后续明确确认的变更为准。
15. 遇到本文件未定义的细节，优先采用本文件中的默认规则并保持实现简单；不得因此阻塞开发，也不得自行引入新的大型技术组件。确实影响业务正确性的冲突，先记录在 `docs/待确认事项.md`，并采用最保守的实现。
16. **先建立可持续的工程骨架，再开发业务。** 不得先堆页面或把所有逻辑写进路由；必须先完成配置管理、数据库会话、迁移、认证授权、统一异常/响应、日志、测试基建和双端请求封装。
17. **数据库结构先行且可追踪。** 所有表结构只能通过 Alembic migration 创建和修改；禁止依赖手工 SQL 初始化正式结构，禁止在应用启动时自动 `create_all()`；每次迁移必须可审查、可升级，并提供必要的回滚策略。
18. **业务规则以后端为唯一权威。** 前端展示、按钮禁用和 Redis 缓存均不能代替后端校验；价格、库存、预约容量、资源归属、角色和状态转换必须由后端重新核验。
19. **所有写操作明确事务边界。** Service 层负责事务提交/回滚；Router 不得自行提交部分业务事务；事务内不得执行耗时文件处理或 WebSocket 网络发送。
20. **先写核心业务测试，再扩展模块。** 对领养审核、预约容量、订单库存、订单支付/关单等并发敏感流程，必须有 Service 层测试和 API 集成测试；没有通过测试不得宣称模块完成。

### 0.2 工程根基与不可妥协的实现顺序

以下要求优先级高于页面数量和视觉效果，必须在业务开发前落实：

1. **配置分环境：** 使用 Pydantic Settings 统一读取环境变量；区分 development/test/production；禁止在源码中写数据库密码、JWT 密钥、管理员真实密码、固定公网地址。
2. **数据库生命周期：** 建立 SQLAlchemy 2.x Engine、SessionLocal 和 `get_db` 依赖；每个 HTTP 请求使用独立 Session；请求结束确保关闭；事务由 Service 明确开启、提交或回滚。异步/同步数据库访问模式必须统一，V1 默认使用同步 SQLAlchemy + PyMySQL，不混用 AsyncSession。
3. **模型与迁移：** 先建立 Base、模型注册入口、命名规范和第一版 Alembic migration；迁移文件必须纳入 Git。禁止生产环境 `create_all()`，禁止直接改数据库后不生成 migration。
4. **统一基础设施：** 先完成统一响应、业务异常、请求 ID、结构化日志、分页、枚举、时间工具、Redis 客户端和文件存储接口，再写业务模块。
5. **分层与依赖方向：** Router → Service → Repository/Session；Schema 不依赖 Router；Model 不依赖 Service；Service 不导入 Vue/前端概念。避免循环依赖和跨模块直接修改内部状态。
6. **数据约束：** 为外键、唯一字段、常用筛选字段建立索引；关键约束尽量由数据库约束兜底，不能只靠前端或 Python 判断。删除历史业务数据采用软删除/停用。
7. **事务原则：** 一个业务动作对应一个明确事务；事务失败整体回滚。事务提交后再发 WebSocket 通知；通知失败不能回滚已经提交的业务。
8. **接口契约：** 每个接口先定义请求 Schema、响应 Schema、权限、错误场景和状态码，再实现；前后端以 OpenAPI 契约联调，不允许双方各自猜字段。
9. **测试基建：** 建立独立测试数据库和测试配置；测试不得连接开发/生产库；每个核心业务模块至少覆盖成功、参数错误、权限/归属错误、状态冲突和并发/重复提交场景。
10. **可重复启动：** README 必须从空环境开始可重复执行；migration、seed、启动和测试命令明确；seed 必须幂等，重复运行不产生重复演示数据。
11. **质量门禁：** 每个阶段至少执行格式/静态检查、后端测试、前端构建和手工流程验证；禁止通过屏蔽异常、删除测试或硬编码返回值来“通过验收”。
12. **最小化依赖：** 只引入当前需求确实需要的库；依赖版本写入锁定文件（Python 使用 requirements 锁定版本或 lock 工具，前端提交 package-lock/pnpm-lock）；不随意升级核心依赖。

**数据库访问默认约定：** V1 使用同步 SQLAlchemy 2.x Session + PyMySQL；FastAPI 路由可声明普通 `def`，避免在 `async def` 中执行阻塞数据库调用。WebSocket/异步任务如需访问数据库，使用独立 Session，并明确关闭。


## 1. 项目概述

### 1.1 项目定位

建设一个面向宠物主人、潜在领养者及平台运营人员的宠物综合服务平台。用户可以浏览待领养宠物、提交领养申请、管理自己的宠物档案、预约宠物医疗、预约洗护或寄养服务，并购买宠物用品。管理员通过管理端维护宠物、服务、医疗资源和商品，审核领养申请、处理预约、管理商品订单。

“智能”体现在信息聚合、条件筛选和业务流程线上化。**V1 不要求训练或接入 AI 模型**，不能把普通筛选包装成 AI 算法。

### 1.2 项目目标

- 建立完整的用户端与管理端前后端分离应用。
- 建立可维护、可迁移的 MySQL 数据结构。
- 用 FastAPI 提供 REST API，使用 JWT 完成身份认证与角色授权。
- 用 SQLAlchemy 2.x 完成 ORM 数据访问，Alembic 管理数据库迁移。
- 使用 Redis 实现购物车及热点数据缓存。
- 使用 WebSocket 向管理端推送新业务提醒。
- 使用后台定时任务自动关闭超时未支付商品订单。
- 支持 Docker Compose 一键启动开发/演示环境。

### 1.3 项目边界

本项目是**单体全栈业务系统**。前端分成两个应用，后端仍然只有一个 FastAPI 服务和一套 MySQL / Redis。模块内部按 router、schema、service、model 分层，避免把所有逻辑堆在路由函数里。


## 2. 技术选型与版本约定

### 2.1 后端

| 技术 | 用途 | 约定 |
|---|---|---|
| Python 3.11+ | 开发语言 | 统一使用类型标注；避免无必要的动态魔法 |
| FastAPI | Web API 框架 | REST API；自动生成 OpenAPI / Swagger 文档 |
| Uvicorn | ASGI 服务器 | 本地开发与容器启动 |
| SQLAlchemy 2.x | ORM / 数据访问 | 优先使用 2.x `select()` 风格；复杂查询允许 SQL |
| Alembic | 数据库迁移 | 所有正式表结构变更必须生成 migration，不以手工改库代替 |
| Pydantic 2 | 请求校验 / 响应模型 | 请求 schema 与 ORM model 分离 |
| PyMySQL | MySQL 驱动 | 与 SQLAlchemy 配合 |
| PyJWT | JWT 编解码 | Access Token；密钥必须从环境变量读取 |
| Passlib | 密码哈希 | 使用 bcrypt 哈希；锁定兼容版本并在项目初始化时验证；数据库不保存明文密码 |
| Redis | 缓存、购物车、轻量临时状态 | 通过统一 Redis 客户端访问，设置合理 TTL |
| APScheduler | 定时关单 | V1 单实例运行；仅启动一个调度器；任务必须幂等 |
| WebSocket | 管理端实时提醒 | FastAPI 原生 WebSocket；V1 单实例连接管理 |
| pytest / httpx | 测试 | 路由、服务、业务流程测试 |

### 2.2 前端

| 技术 | 用途 | 约定 |
|---|---|---|
| Vue 3 | 前端框架 | Composition API + `<script setup>` |
| Vite | 构建工具 | 分别构建管理端和用户端 |
| Element Plus | UI 组件 | 管理端优先使用表格、表单、弹窗、分页组件 |
| Vue Router | 路由 | 路由守卫处理登录和权限 |
| Pinia | 状态管理 | 登录用户、Token、必要的全局状态 |
| Axios | HTTP 请求 | 统一封装 baseURL、Token、错误处理 |
| ECharts（可选） | 管理端统计图表 | 核心业务完成后再加入 |
| ESLint + Prettier | 代码规范 | 两个前端项目使用一致规范 |

### 2.3 数据库与基础设施

- **MySQL 8.0：** 唯一业务主库，保存用户、宠物、申请、预约、商品、订单、地址、通知等持久化数据。所有业务事实以 MySQL 为准。
- **Redis：** 保存购物车、热点分类/列表缓存、WebSocket 辅助信息。Redis 数据丢失后业务主数据仍必须完整。
- **文件存储：** V1 默认使用后端本地 `uploads/` 目录并通过静态资源路径访问；生产部署将上传目录挂载为持久化卷。接口封装存储服务，后续可切换 OSS，但 V1 不强制购买云存储。
- **Docker Compose：** 统一编排 MySQL、Redis、后端、两个前端静态站点和 Nginx（可按开发环境简化）。
- **Nginx：** 反向代理 `/api/`、`/ws/`，并托管两个前端静态页面或分别配置站点。

### 2.4 禁止引入的技术

V1 不引入 Spring Boot、Django、Node.js 后端、微服务框架、注册中心、Kafka/RabbitMQ、Elasticsearch、Kubernetes、真实支付 SDK。需要新增依赖时，先确认是否属于核心必要项。


## 3. 用户角色与权限

### 3.1 角色

| 角色 | 说明 | 入口 |
|---|---|---|
| 游客 | 未登录用户；可浏览公开宠物、服务项目和商品 | 用户端 |
| USER | 注册并登录的普通用户；可管理个人资料/宠物、提交申请和预约、购买商品 | 用户端 |
| ADMIN | 平台管理员；管理基础数据、审核申请、处理预约和订单 | 管理端 |

### 3.2 权限原则

- 游客只允许访问公开查询接口，不允许创建申请、预约、购物车和订单。
- USER 只能查看/修改自己的资料、宠物档案、申请、预约、订单、地址和购物车。
- ADMIN 可访问管理端接口；管理接口统一使用 `/api/v1/admin/` 前缀。
- 后端必须校验权限，不能只依赖前端隐藏菜单。
- 管理员账号通过初始化脚本或 seed 命令创建，不允许公开注册管理员。
- V1 不实现医生、门店员工、供应商等独立角色。医疗人员信息由管理员维护。


## 4. 功能范围与页面需求

## 4.1 用户端（user-web）

### 4.1.1 公共与账号模块

- 首页：展示平台介绍、领养推荐列表、服务入口、热门用品。
- 注册：手机号或用户名（二选一即可，V1 默认用户名 + 手机号可选）；密码加密后存库；用户名唯一。
- 登录/退出：账号密码登录，成功后返回 JWT。
- 个人中心：查看和修改昵称、头像、手机号（手机号可选）、个人简介。
- 我的宠物：新增、编辑、查看、删除本人宠物档案；已关联预约/订单的宠物不物理删除，改为停用或软删除。
- 我的消息：查看平台通知（如实现通知列表）；WebSocket 实时提醒以管理端为主。

### 4.1.2 宠物领养模块

- 领养列表：分页展示可申请领养的宠物。
- 筛选：按宠物类别、性别、年龄区间、城市/地区、健康状态、关键字筛选。
- 详情：宠物名称、照片、品种、性别、年龄、体重、健康情况、疫苗/绝育信息、性格描述、领养要求、所在地区、发布时间和当前状态。
- 申请：登录用户填写申请理由、居住环境、养宠经验、联系方式等；同一用户对同一宠物只能有一条未结束申请。
- 进度：用户可以查看自己的申请状态及管理员审核意见。
- 撤回：仅允许撤回待审核申请；已通过/已拒绝/已完成的申请不能撤回。
- 领养结果：管理员审核通过后，宠物进入“已领养/不可申请”状态，避免重复领养。

**领养规则：**

1. 只有状态为 `AVAILABLE` 的宠物可以提交申请。
2. 用户必须登录；用户必须填写完整的必填申请信息。
3. 同一宠物可以有多条待审核申请，但同一用户对同一宠物最多一条待审核申请；创建申请时锁定宠物记录并在事务内检查该用户是否已有待审核申请，避免并发重复提交。
4. 管理员一次只能将该宠物的一条申请审核为通过；审核通过时必须在事务中将宠物改为 `ADOPTED`，并将同宠物其他待审核申请统一置为 `CLOSED`（保存关闭原因）。
5. 审核拒绝必须填写拒绝原因；审核通过必须记录审核人和审核时间。
6. 宠物已下架、已领养或审核状态不允许时，接口必须拒绝申请。

### 4.1.3 宠物医疗预约模块

- 医疗服务列表：展示可预约医疗项目，如体检、疫苗、驱虫、基础诊疗预约（仅预约，不在线问诊）。
- 诊所/医疗点列表：展示名称、地址、联系电话、营业说明。
- 医生列表：按医疗点查看医生姓名、头像、擅长说明及可预约时段。
- 可预约时段：按日期查看医生排班、开始时间、结束时间、剩余名额。
- 提交预约：选择本人宠物、医疗点、医疗项目、医生/时段，填写症状说明（可选）和联系电话。
- 我的医疗预约：查看预约详情与状态；待确认预约允许用户取消。
- 管理端确认或拒绝预约；拒绝需填写原因。

**医疗预约规则：**

- 仅展示启用的医疗点、医生、项目和未满额时段。
- 创建预约时必须在数据库事务中使用 `SELECT ... FOR UPDATE` 锁定排班记录并检查时段仍开放、未过期且剩余容量充足，防止超卖；同一用户重复提交同一时段时应返回明确冲突。
- 用户取消或管理员拒绝时释放已占用名额；完成预约后不再释放。
- V1 不提供在线诊断、处方、病历和医疗费用真实支付。
- 时间统一按项目配置的业务时区保存和展示；数据库存储规则应在配置中统一，不允许前后端各自随意转换。

### 4.1.4 洗护 / 寄养服务模块

- 服务分类：洗澡、美容、剪毛、护理、寄养等。
- 服务套餐列表：名称、封面、说明、价格、服务时长、适用宠物、预约须知。
- 服务详情：展示详细介绍、价格、时长和预约规则。
- 创建预约：选择本人宠物、服务套餐、日期/时段、联系人、联系电话和备注。
- 寄养预约额外填写：预计入住日期、预计离店日期、特殊照护要求。
- 我的服务预约：查看状态、预约信息、管理员处理意见；待确认状态可取消。
- 管理端维护服务分类和套餐、确认/拒绝预约、标记服务完成。

**服务预约规则：**

- 已下架服务不可预约。
- 预约时间不得早于当前时间；寄养离店日期必须晚于入住日期。
- V1 可先采用管理员人工确认，不实现复杂资源排班和自动容量算法。
- 如果同一时段限制名额，必须使用数据库事务锁定名额；若未配置容量，则按人工确认处理。
- V1 服务预约不接真实支付；价格作为预约下单时的价格快照保存。

### 4.1.5 宠物用品商城模块

- 商品分类：展示启用分类。
- 商品列表：分页、关键字、分类筛选、价格排序（可选）。
- 商品详情：名称、主图、轮播图、详情描述、价格、库存、规格说明、上下架状态。
- 购物车：登录用户添加、修改数量、勾选、删除、查询；数据存 Redis。
- 收货地址：新增、编辑、删除、设置默认地址。
- 提交订单：校验商品上架状态、价格、库存和地址，生成订单及订单明细；将商品名称、单价等保存快照。
- 订单列表/详情：查看订单状态与明细。
- 模拟支付：只用于本地演示，点击后将订单标记为已支付；必须有明显“模拟支付”字样。
- 取消订单：未支付订单可主动取消，并释放库存。
- 确认收货：已发货订单可由用户确认收货，状态变为完成。

**商城规则：**

1. 购物车使用 Redis，不作为订单数据源。下单时必须重新从 MySQL 读取商品和价格，不能信任前端或 Redis 中的价格。
2. 下单接口必须支持客户端 `Idempotency-Key`（或等价请求幂等号），同一用户同一幂等号重复请求只能返回同一订单，不得重复扣库存。下单必须在事务中校验库存并扣减库存；建议使用 `UPDATE products SET stock = stock - :qty WHERE id = :id AND status = 'ON_SALE' AND stock >= :qty` 并检查影响行数。任一商品扣减失败，整个订单事务回滚。
3. 商品价格使用 `DECIMAL`，不得使用浮点数存钱。
4. 商品订单创建后默认状态 `PENDING_PAYMENT`，30 分钟未模拟支付自动关闭并释放库存。
5. 模拟支付接口只允许支付属于当前用户且状态为 `PENDING_PAYMENT` 且未超时的订单；重复请求应幂等。支付成功必须通过状态条件更新完成，只允许一次从 `PENDING_PAYMENT` 变为 `PAID`。
6. 管理员发货时填写物流公司和单号（可选字段，不对接真实物流）；用户确认收货后完成订单。
7. V1 不接真实微信/支付宝支付、退款接口和物流轨迹接口。

## 5. 核心业务流程与状态机

### 5.1 领养申请流程

1. 管理员创建宠物档案并上架，宠物状态变为 `AVAILABLE`。
2. 用户浏览详情并提交申请，申请状态变为 `PENDING`。
3. 管理员审核：通过则申请变为 `APPROVED`，宠物变为 `ADOPTED`，同宠物其他待审核申请统一变为 `CLOSED`；拒绝则申请变为 `REJECTED`，宠物保持可申请状态（仍上架时）。
4. 用户仅可在待审核阶段主动撤回，申请状态变为 `CANCELLED`。

状态定义：

| 对象 | 状态 | 含义 |
|---|---|---|
| 宠物 | `DRAFT` | 草稿，不对用户展示 |
| 宠物 | `AVAILABLE` | 已上架，可申请 |
| 宠物 | `OFFLINE` | 已下架，不可申请 |
| 宠物 | `ADOPTED` | 已领养，不可再申请 |
| 领养申请 | `PENDING` | 待审核 |
| 领养申请 | `APPROVED` | 审核通过 |
| 领养申请 | `REJECTED` | 审核拒绝 |
| 领养申请 | `CANCELLED` | 用户撤回 |
| 领养申请 | `CLOSED` | 因同宠物其他申请已通过而关闭 |

### 5.2 医疗预约流程

1. 用户选择医疗点、项目、医生和时段并提交预约。
2. 后端在数据库事务中锁定排班记录，检查时段有效且剩余容量充足。
3. 创建 `PENDING_CONFIRMATION` 预约，并将排班 `booked_count` 加 1。
4. 事务提交成功后通过 WebSocket 提醒管理员。
5. 管理员确认后变为 `CONFIRMED`，拒绝后变为 `REJECTED`；服务完成后标记 `COMPLETED`。

用户在待确认状态可以取消为 `CANCELLED`。管理员拒绝、用户取消均释放时段名额。确认之后如需取消，V1 允许管理员处理并释放名额；用户侧只允许取消待确认预约，减少边界复杂度。

### 5.3 洗护 / 寄养预约流程

1. 用户选择服务套餐、本人宠物和服务时间，填写联系人及备注。
2. 后端校验套餐状态、宠物归属和预约时间，创建 `PENDING_CONFIRMATION` 预约，并保存价格快照。
3. 事务提交成功后通过 WebSocket 提醒管理员。
4. 管理员确认后变为 `CONFIRMED`，拒绝后变为 `REJECTED`；服务完成后标记 `COMPLETED`。

预约价格和套餐名称必须保存快照，避免后续套餐改价影响历史预约。

### 5.4 商品订单流程

1. 用户从 Redis 购物车发起结算。
2. 后端重新读取 MySQL 商品价格、上下架状态和库存，不信任前端或 Redis 中的金额。
3. 数据库事务内扣减库存、创建订单及订单明细，订单状态为 `PENDING_PAYMENT`。
4. 用户可执行模拟支付，订单变为 `PAID`；管理员发货后变为 `SHIPPED`；用户确认收货后变为 `COMPLETED`。
5. 用户主动取消或订单超过 30 分钟未支付，订单变为 `CANCELLED` / `CLOSED`，并在同一事务中释放库存。

订单状态：

| 状态 | 说明 | 允许的下一步 |
|---|---|---|
| `PENDING_PAYMENT` | 待模拟支付 | `PAID` / `CANCELLED` / `CLOSED` |
| `PAID` | 已支付（模拟） | `SHIPPED` |
| `SHIPPED` | 已发货 | `COMPLETED` |
| `COMPLETED` | 已完成 | 终态 |
| `CANCELLED` | 用户取消 | 终态 |
| `CLOSED` | 超时自动关单 | 终态 |

**库存策略：** 创建待支付订单时立即预扣库存；取消/超时关闭时归还库存；模拟支付成功不再扣库存。订单状态变更和库存归还必须在同一数据库事务中完成，并通过状态条件更新保证只执行一次。订单创建幂等键必须持久化在订单表并建立用户维度唯一约束，不能只用 Redis 短期锁保证下单幂等。

### 5.5 WebSocket 事件

WebSocket 地址：`/ws/admin/notifications`。连接建立后客户端必须在 5 秒内发送认证首帧（包含 access token），服务端验证 JWT 且角色为 ADMIN 后才注册连接；认证失败立即关闭连接。禁止把 JWT 放在 URL query 中，避免被代理日志、监控和访问记录泄露。生产环境必须使用 WSS。

事件示例：

```json
{
  "event": "NEW_BUSINESS",
  "business_type": "ADOPTION_APPLICATION",
  "business_id": 10001,
  "title": "收到新的领养申请",
  "created_at": "2026-01-01T10:00:00+08:00"
}
```

`business_type` 取值：`ADOPTION_APPLICATION`、`MEDICAL_APPOINTMENT`、`SERVICE_BOOKING`、`PRODUCT_ORDER`。WebSocket 推送只传提醒摘要和业务 ID，不推送用户密码、证件等敏感资料。


## 6. 数据库设计

### 6.1 数据库规范

- 数据库：`pet_platform`，MySQL 8.0，统一 `utf8mb4`。
- 主键：`BIGINT` 自增 ID（或统一雪花 ID，V1 默认自增 ID）。
- 金额：`DECIMAL(10,2)`，Python 使用 `Decimal`。
- 时间：MySQL 使用 `DATETIME`，应用层统一按 UTC 写入和读取；API 输入输出使用带时区的 ISO 8601 时间字符串；用户界面统一按 `Asia/Shanghai` 展示。禁止将无时区时间在不同层重复转换。业务时区固定为 `Asia/Shanghai`，排班日期/营业时段按业务时区解释，再转换为 UTC 时间点保存。
- 通用字段：`created_at`、`updated_at`；必要表增加 `deleted` 软删除标记。
- 外键：核心关系建立索引；删除有业务历史的记录时优先停用或软删除，不物理级联删除订单/申请。核心外键应在 MySQL 中建立真实 FK 约束；跨业务历史记录不得配置级联物理删除。
- 状态字段使用字符串枚举，避免前后端对数字状态含义不一致。
- 所有业务表由 SQLAlchemy Model 定义并使用 Alembic 迁移。

### 6.2 表清单

| 表名 | 说明 | 主要关联 |
|---|---|---|
| `users` | 用户账号、角色、状态、密码哈希 | 关联宠物、申请、预约、订单、地址 |
| `user_pets` | 用户自己的宠物档案 | `users.id` |
| `pet_categories` | 领养宠物分类 | 关联 `adoption_pets` |
| `adoption_pets` | 平台待领养宠物档案 | `pet_categories.id` |

### 6.4 Redis Key 约定

| Key | 类型 | 用途 | TTL |
|---|---|---|---|
| `pet:cart:{user_id}` | Hash | 用户购物车，field 为 product_id，value 为数量/必要摘要 | 30 天，可续期 |
| `cache:pet:categories` | String/JSON | 领养宠物分类 | 10 分钟 |
| `cache:product:categories` | String/JSON | 商品分类 | 10 分钟 |
| `cache:service:packages` | String/JSON | 启用服务套餐列表 | 5 分钟 |
| `ws:admin:online:{admin_id}` | String | 管理员在线临时状态（可选） | 心跳 TTL |

Redis 缓存必须设置过期时间。管理员修改商品、分类、服务数据后及时清理相关缓存。购物车结算成功后清空已购买项目；若下单失败不得误清空购物车。

### 7.2 后端分层职责

- `api/`：只负责 HTTP 参数接收、依赖注入、调用 Service、返回响应；不写复杂业务规则。
- `schemas/`：请求/响应数据模型；禁止直接把 SQLAlchemy ORM 对象原样返回给前端。
- `models/`：数据库 ORM 表结构和关系。
- `repositories/`：可复用查询封装；简单查询可以由 Service 直接使用 Session，但复杂查询应抽取。
- `services/`：核心业务规则、状态校验、事务提交边界；领养审核、库存扣减、名额扣减等必须在 Service 层实现。
- `core/`：配置、数据库、Redis、安全、依赖和异常处理等基础能力。
- `tasks/`：定时任务。任务与业务逻辑复用同一 Service，不重复写一套订单状态更新逻辑。
- `websocket/`：连接管理、事件推送；不承载业务数据持久化。

### 7.3 接口统一规范

- API 前缀：`/api/v1`。
- 用户接口：`/api/v1/user/...`。
- 管理接口：`/api/v1/admin/...`。
- 公开查询可放在 `/api/v1/public/...`，也可放用户端公开路由，但必须明确无需登录。
- 请求与响应统一 JSON；文件上传使用 `multipart/form-data`。
- 分页参数统一：`page` 从 1 开始，`page_size` 默认 10，最大 100。
- 列表响应统一返回 `items`、`total`、`page`、`page_size`。

**统一响应示例：**

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "id": 10001
  }
}
```

**分页响应示例：**

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "items": [],
    "total": 0,
    "page": 1,
    "page_size": 10
  }
}
```

业务错误使用明确错误码和可读 message，例如 `40001` 参数错误、`40100` 未登录/Token 失效、`40300` 无权限、`40400` 资源不存在、`40900` 状态冲突、`50000` 服务异常。HTTP 状态码也应合理使用，不能所有错误都返回 200。响应中的 `code` 是业务码，HTTP status 表达协议层结果，两者不得混为一谈。

### 7.4 API 接口清单（V1 必须覆盖）

#### 账号与个人资料

- **POST** `/api/v1/admin/auth/login`（游客）：管理员登录

- **PUT** `/api/v1/user/pets/{id}`（所属 USER）：修改宠物档案

## 8. 前端实现规范

### 8.1 两个独立前端的边界

- `admin-web`：仅用于管理员操作；默认首页跳转登录页或工作台；采用后台管理布局（侧边栏 + 顶栏 + 内容区）。
- `user-web`：面向消费者；首页、列表、详情、个人中心采用用户端布局，适配常见桌面浏览器和移动端宽度。
- 两个项目可以复制少量基础工具，但不得把管理端菜单或用户端页面混成一个应用。

### 8.2 前端目录职责

- `api/`：按业务模块封装请求函数；组件内禁止散落 URL 字符串。
- `stores/`：Pinia 管理登录用户、Token 和用户状态。
- `router/`：路由定义、登录守卫、角色守卫。
- `views/`：页面；按业务模块拆分。
- `components/`：可复用组件，如上传、分页、状态标签、确认弹窗。
- `utils/request.js`：Axios 实例、Token 注入、统一错误处理。

### 8.3 登录与 Token

- 登录成功后按当前 V1 演示方案保存 Access Token；请求拦截器自动添加 `Authorization: Bearer <token>`。Token 仅保存必要字段，不保存密码；生产环境若采用 HttpOnly Cookie，必须同步调整 CSRF 防护、CORS 和 WebSocket 认证方案。
- 退出登录清理 Token 和 Pinia 状态。
- 收到 401 时清理登录态并跳转登录页；收到 403 时显示无权限提示。
- Token 过期时间通过后端配置；V1 可以先只实现 Access Token，不强制 Refresh Token。
- 不把密码、密钥写入前端代码或提交到 Git。

### 8.4 UI 行为规范

- 所有表格必须具备加载状态、空状态、错误提示和分页（适用时）。
- 表单必须有前端基础校验，后端仍需再次校验。
- 删除、拒绝、下架、关单等危险操作须二次确认。
- 提交按钮请求期间禁用，防止重复提交。
- 图片上传显示进度或加载状态，并限制大小与格式。
- 价格统一显示两位小数；状态统一映射中文文本和标签样式。
- 不允许使用大量写死的演示数据代替后端接口；初始化演示数据必须通过 seed 脚本写入数据库。


## 9. 安全、异常与工程质量

### 9.1 安全要求

- 密码仅存哈希，登录使用 Passlib 验证。
- JWT Secret 从 `.env` 读取；生产使用足够长度的随机密钥。
- 所有管理端路由校验 `ADMIN` 角色；所有用户私有资源校验资源所属用户 ID。
- SQL 查询使用 SQLAlchemy 参数绑定，禁止拼接用户输入形成 SQL。
- 上传文件校验扩展名、MIME、大小，生成随机文件名，不信任用户原始文件名；禁止上传可执行脚本。
- CORS 仅开放配置中允许的前端域名，不使用生产环境全量 `*`。
- 对登录、注册、上传等接口设置基本限流或频率保护（可先采用轻量实现）。
- 日志不得输出密码、JWT 完整值、支付密钥或用户敏感字段。
- 所有用户输入后端再次验证；库存、预约容量、状态转换由后端决定。

### 9.2 事务与并发要求

下列操作必须在数据库事务中完成：

1. 领养审核通过：锁定宠物记录、核验 `AVAILABLE`、更新宠物状态、更新申请状态、关闭其他申请。
2. 医疗预约创建/取消/拒绝：锁定排班记录、检查容量、更新 `booked_count`、保存预约状态。
3. 商品订单创建：校验商品状态/价格/库存、扣减库存、创建订单和订单明细、记录库存流水。
4. 商品订单取消/超时关单：条件更新订单状态、释放库存、写库存流水。
5. 设置默认收货地址：清除旧默认并设置新默认。

所有“通过状态判断再更新”的操作应使用行锁或带状态条件的 UPDATE，检查影响行数并在必要时使用唯一约束，避免并发请求造成重复审核、重复支付、重复扣减或重复返还。库存变更必须同时写入库存流水；库存流水失败则业务事务回滚。

### 9.3 异常处理

- 统一全局异常处理器，将参数异常、业务异常、权限异常、数据库异常转成统一响应。
- 对用户展示可理解的错误消息；日志记录堆栈和请求 ID，不向用户暴露 SQL、文件路径和密钥。
- 对重复提交返回明确的状态冲突，不要创建重复订单/预约。
- 所有列表接口提供合理分页上限，防止一次性拉取全表。


## 10. 文件上传与图片规范

- 上传接口返回可访问的相对 URL，例如 `/uploads/pets/随机文件名.jpg`。
- 领养宠物图片、商品图片、用户头像、用户宠物头像统一通过文件服务处理。
- V1 本地实现 `LocalStorage`；通过 Storage 接口隔离业务层，未来可切换 OSS。
- 建议图片格式：jpg、jpeg、png、webp；单张图片默认不超过 5 MB（可配置）。
- 文件名使用 UUID；原始文件名仅可作为元数据，不直接拼接磁盘路径。
- Docker 部署时将 `server/uploads` 挂载到持久化 Volume；容器重启不得导致图片丢失。
- 未使用的图片清理作为可选维护任务，不影响核心功能。


## 11. 定时任务与 WebSocket 实施细则

### 11.1 定时关单

- 默认超时：创建订单后 30 分钟。
- 任务频率：每分钟扫描待支付且 `created_at <= now - 30 minutes` 的订单。
- 任务调用订单 Service 的 `close_expired_order()`，不得绕过 Service 自行改状态。
- 通过 `WHERE status='PENDING_PAYMENT'` 条件更新或行锁保证幂等。
- 只有成功从 `PENDING_PAYMENT` 改成 `CLOSED` 的订单才释放库存。
- 用户主动取消和定时关单并发发生时，只允许一个操作成功释放库存。
- 任务执行日志记录扫描数量、关闭数量和失败订单；单个订单失败不得中断全部任务。
- V1 单实例启动 APScheduler；启动时必须保证只有一个调度器实例。若后续多进程/多副本部署，必须改为独立 scheduler 进程或分布式锁，并增加任务执行记录；不能简单地让每个 Uvicorn worker 都启动一个调度器。

### 11.2 WebSocket

- 后端启动连接管理器，按管理员用户 ID 保存连接。
- 建连后 5 秒内验证客户端认证首帧中的 JWT，且角色必须为 `ADMIN`；未认证连接不得订阅或接收事件。
- 新业务提交事务成功后发送事件，禁止在数据库提交前发送“已创建”通知。
- 发送失败不回滚已成功业务；前端重连后通过 REST 接口同步待处理列表。
- 前端每隔一段时间可发送 ping 或使用 WebSocket 心跳，服务端清理断开连接。
- 记录连接异常，不记录 Token 原文。

### 13.2 演示流程

8. 创建一笔未支付订单，通过测试配置缩短关单时间或直接调用任务验证超时关单，确认库存返还一次。


## 14. 测试与验收标准

### 14.1 后端测试

- 注册：重复用户名失败；密码以哈希形式保存。
- 登录：错误密码失败；正确账号返回 Token。
- 权限：USER 访问管理接口 403；未登录访问受保护接口 401。
- 数据隔离：用户 A 不得查看、修改用户 B 的宠物、申请、预约、订单和地址。
- 领养：宠物非 `AVAILABLE` 时不能申请；重复申请受控；审核通过后宠物状态正确；同宠物其他待审核申请关闭。
- 医疗预约：排班容量已满时不能预约；并发预约不得超过容量；取消/拒绝后释放名额。
- 服务预约：下架套餐不能预约；寄养离店日期必须晚于入住日期；历史价格不随套餐改价变化。
- 购物车：Redis 增删改查正确；购物车价格不能直接决定订单价格。
- 商品订单：库存不足下单失败；下单后库存减少；取消/关单只返还一次；模拟支付不能重复支付或给他人订单支付。
- 定时任务：超时订单关闭；未超时订单不关闭；已支付订单不关闭；库存返还幂等。
- WebSocket：只有管理员可连接；新业务提交成功后可收到对应事件。

### 14.2 前端验收

- 两个前端可独立启动、构建。
- 刷新页面后登录状态按 Token 策略恢复；Token 失效可正确退出。

- 用户端在常见移动端宽度下无明显横向溢出。

### 14.3 部署验收

## 18. 基础工程强制规范

本章是项目质量底线。功能数量、开发速度和页面效果不得凌驾于本章要求之上。

### 18.1 代码组织与依赖边界

- 一个 FastAPI 应用、一个 MySQL 主库、一个 Redis 实例；按业务模块组织，不拆服务。
- Router 只处理 HTTP；Service 实现业务规则并管理事务；Repository 负责可复用查询；Model 只描述持久化结构；Schema 负责输入输出校验。
- 禁止在 Router 中直接写多表业务事务；禁止在 Vue 组件中拼接业务规则；禁止把 SQLAlchemy Model 直接作为 API 响应。
- 模块之间通过 Service 接口协作，不得跨模块随意修改对方数据；跨模块事务必须有明确的业务 Service 入口。

### 18.2 数据库与迁移纪律

- 先建 ER 关系和核心字段，再编写模型；模型、迁移、数据库实际结构必须一致。
- 每次 schema 变更提交 migration；迁移前检查已有数据兼容性；删除/重命名字段必须考虑数据迁移，不得直接破坏历史数据。
- 所有金额使用 `DECIMAL` + Python `Decimal`；数量、容量必须校验正数及上下限；所有时间统一遵守 UTC 存储约定。
- 核心业务关系建立外键、唯一约束和索引；关键业务不能只依赖应用层 if 判断。
- 生产环境禁止自动执行破坏性迁移；部署前先备份数据库并审查 migration。

### 18.3 事务、并发与幂等

- 领养审核、排班名额、商品库存、订单支付、取消和超时关单均为并发敏感操作，必须通过事务、行锁或条件更新保护。
- 对外部重复请求有副作用的创建接口应支持幂等键或业务唯一性校验。
- 库存扣减与释放必须有流水；库存释放必须与订单状态迁移在同一事务内，且只允许成功迁移状态的一方执行。
- WebSocket、文件存储等非数据库副作用放在数据库提交之后；失败时记录日志并提供补偿/重试路径，不得伪造成功。

### 18.4 API 与前端契约

- 所有接口明确：路径、方法、权限、请求字段、响应字段、HTTP 状态码、业务错误码和副作用。
- 分页、排序、筛选参数有统一约束；后端设置最大 page_size；排序字段使用白名单，禁止把用户输入直接拼入 SQL。
- 前端统一 Axios 实例、Token 处理、错误提示、请求取消/重复提交保护；页面不能直接访问数据库或 Redis。
- 对用户可见的业务状态统一由枚举映射，状态中文文案不得在多个组件中重复硬编码。

### 18.5 安全与数据保护

- 所有私有资源查询都必须同时校验登录用户和资源归属；仅凭前端传入的 user_id 不构成授权。
- 密码、Token、密钥、手机号等敏感信息不得写入普通日志；密码永不返回 API。
- 上传文件限制大小、类型和文件名；静态文件目录不得执行脚本；文件路径必须防止目录穿越。
- 管理员初始化凭据仅从环境变量读取，首次部署后应更换；生产环境关闭 Debug 和 Swagger（或通过访问控制保护）。
- CORS 采用明确白名单；Cookie 方案如启用需配置 SameSite、Secure、HttpOnly 和 CSRF 防护。

### 18.6 测试与交付门禁

每个业务模块完成时，必须提供：

1. Alembic migration（涉及表结构时）；
2. Pydantic 请求/响应 Schema；
3. Service 层业务实现；
4. Router/API 接口及权限校验；
5. pytest 自动化测试；
6. 前端页面与真实 API 联调；
7. README 或模块说明更新。

进入下一个模块前必须满足：后端测试通过、前端构建通过、核心流程可手工复现、无未解释的控制台错误。禁止用 mock 数据替代已经要求接入的真实业务接口。

### 18.7 AI 开发执行纪律

- 每次只实现一个可验收的小阶段，完成后汇报：修改文件、实现内容、执行命令、测试结果、已知问题。
- 修改已有结构前先检查当前仓库，不得覆盖用户已有代码或配置；不确定时先保留并兼容。
- 不得一次性生成大量未经运行验证的代码；不得跳过 migration、测试或 README。

- 本文档未明确的内容，先采用最简单且安全的默认实现，并记录到 `docs/待确认事项.md`；只有影响数据安全、资金/库存正确性或核心流程时才暂停并请求确认。
